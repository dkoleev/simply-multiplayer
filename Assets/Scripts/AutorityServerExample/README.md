# RTS: deterministic lockstep с авторитарным сервером

Учебный пример сетевой RTS-логики. Сервер и клиенты крутят **одну и ту же детерминированную
симуляцию**, а по сети ходят только **приказы игроков**, а не позиции юнитов.

Ядро (`Core/`) — чистый C# без `UnityEngine` (asmdef с `noEngineReferences: true`), поэтому
каждый файл можно положить в gist отдельно, а тесты гоняются хоть в Unity, хоть через `dotnet test`.

## Как запустить

1. Открыть сцену `Assets/Scenes/test_autority_server.unity`, нажать Play.
2. Слева клиент A (он подключается сразу), справа клиент B. Нажать **Join** у клиента B:
   это late join, клиент получает snapshot мира и дальше идёт вместе со всеми.
3. ЛКМ — выделить юнита (или рамкой), ПКМ — приказ на движение, `S` — стоп.
4. Слайдерами можно менять задержку и джиттер каждого клиента на лету.
5. **Corrupt local state** ломает детерминизм у клиента: сервер ловит расхождение хэша
   и отправляет snapshot (ресинк). Всё видно в логе внизу.
6. В Scene view жёлтые сферы — мир сервера: он всегда чуть впереди клиентов.

Тесты: Window → General → Test Runner → EditMode → `Rts.Lockstep.Tests`.

## Как это работает

```
 Client A               Server (20 ticks/s)                Client B
    |                        |                                 |
    |-- Command(Move) ------>|  pending: [Move A]              |
    |                        |                                 |
    |                     tick 41: seal frame                  |
    |<----- TickFrame 41 [Move A] ---------------------------->|
    |                        |  Simulation.Step(world, frame)  |
    | Step(world, frame 41)  |                                 | Step(world, frame 41)
    |                        |                                 |
    |-- StateHash(50, X) --->|  X == hash[50] ? ok : Snapshot  |
```

1. **Клиент не применяет свой ввод сам.** Клик превращается в `Command` и уходит на сервер.
2. **Сервер владеет временем и порядком.** Каждые 50 мс он «запечатывает» кадр `TickFrame N`
   со всеми приказами, пришедшими к этому моменту (даже если их ноль), и рассылает всем.
   `PlayerId` проставляет сервер по соединению — клиент не может отдать приказ за другого.
3. **Клиент симулирует тик N только когда получил кадр N.** Нет кадра — клиент ждёт (stall),
   а не угадывает. Небольшой jitter buffer (`TargetBufferedFrames`) сглаживает неровную доставку,
   а при отставании (`MaxBufferedFrames`) клиент догоняет, прокручивая несколько тиков за кадр.
4. **Одинаковый вход + детерминированный код = одинаковый мир.** `Simulation.Step` у всех один.
5. **Проверка.** Каждые 10 тиков клиент шлёт хэш мира. Не совпал — десинк (баг или читер),
   сервер как авторитет отправляет свой snapshot.
6. **Рендер** идёт на 60+ FPS, симуляция на 20 Гц — `ClientView` интерполирует между двумя последними тиками.

## Правила детерминизма (что нельзя делать в `Simulation`)

| Нельзя | Почему | Вместо этого |
|---|---|---|
| `float`, `Vector3`, `Mathf` | результат зависит от CPU/компилятора (x87, FMA, IL2CPP vs Mono) | `Fix64` / `FixVec2` (Q48.16 в `long`) |
| `UnityEngine.Random`, `System.Random` без общего seed | разные числа у разных пиров | детерминированный PRNG, seed в состоянии мира |
| перебор `Dictionary` / `HashSet` | порядок не гарантирован | `List`, отсортированный по `Id` |
| `Time.deltaTime`, `DateTime` | у каждого своё | фиксированный тик, `world.Tick` |
| ссылки на view, ввод, сеть | внешнее состояние | всё нужное лежит в `World` или приходит в `Command` |

`float` можно использовать на входе (клик мыши → `Fix64.FromFloat` на одной машине, дальше по сети
летит точный `long`) и на выходе (рендер через `ToFloat()`), но не внутри симуляции.

## Файлы (порядок для презентации / gists)

| Файл | О чём |
|---|---|
| `Core/Fix64.cs`, `Core/FixVec2.cs` | fixed-point математика, почему не float |
| `Core/World.cs` | состояние, хэш (FNV-1a), snapshot |
| `Core/Command.cs` | приказ игрока — это всё, что шлёт клиент |
| `Core/Simulation.cs` | детерминированный тик: `(world N, commands N) -> world N+1` |
| `Core/Protocol.cs` | формат сообщений и `TickFrame` |
| `Core/LockstepServer.cs` | часы, порядок, авторитет, проверка хэшей, ресинк |
| `Core/LockstepClient.cs` | ожидание кадров, jitter buffer, catch-up, отправка хэшей |
| `Core/SimulatedNetwork.cs` | фейковая сеть с задержкой/джиттером (заменяется на сокеты) |
| `Demo/RtsDemo.cs`, `Demo/ClientView.cs` | склейка в Unity: split screen, ввод, интерполяция, UI |
| `Tests/LockstepTests.cs` | доказательство: одинаковые хэши, late join, ловля десинка |

## Компромиссы и что дальше

- **Задержка ввода = RTT до сервера.** Для RTS это нормально (StarCraft, Age of Empires) — её прячут
  мгновенным откликом: маркер клика, звук «Yes, sir!». Для экшена нужна prediction + rollback
  (Photon Quantum, GGPO): клиент симулирует вперёд с предсказанным вводом и откатывается при расхождении.
- **Трафик почти не зависит от числа юнитов**: 1000 юнитов стоят столько же, сколько 10.
  Цена — полный мир у каждого клиента (maphack возможен, нужен fog of war на уровне данных / сервера).
- **Реплеи бесплатно:** сохранить все `TickFrame` = записать матч. Проиграть = прогнать `Simulation.Step` заново.
- **Транспорт** должен быть reliable + ordered: потеря кадра — стоп или десинк.
  В проде обычно UDP со своим reliable-каналом и избыточностью (кадр N шлётся вместе с N-1, N-2).
- Сервер можно облегчить до чистого relay (без симуляции), но тогда он не сможет выдавать snapshot'ы
  и проверять хэши — авторитет переходит к «большинству» клиентов.
